# 初期版の開発仕様案

[R-18 の実現可能性評価](../findings/R-18-feasibility.md)を開発範囲に落とし込んだ案。2026-11-24（JST）。依頼者の Go 判断後に開発へ移る。実データ公開、定期取得、有効化する公開先はそれぞれ該当条件の確認と承認を要する。

2026-11-25（JST）に、直近6か月の週次履歴と、同じリポジトリの GitHub Actions から GitHub Pages へ配布する構成を採用した。初回公開の条件と手順は[運用手順案](../operations/mvp-release.md)を参照。

## 画面と静的 URL

表のパスはサイトの基準パスからの相対。プロジェクト配信では `/japan-infection-watch/` の配下。公開する地域・疾患は、承認済みのコード・地区名マスターとデータの対象範囲に基づき生成する。

| 静的 URL | 表示・操作 |
|---|---|
| `/` | 全国の全収録疾患の週次推移と疾患別の週次表、最新週の疾患一覧、都道府県名の検索、公式出典。全国計は公式値。 |
| `/prefectures/{prefecture-code}/` | 都道府県の最新値、全収録疾患の週次推移、疾患別の週次表、出典と鮮度。同じ系列と対象週で全国の値を参照できる。 |
| `/diseases/{disease-id}/` | 疾患の対象となる定点区分、全国の週次推移、同一指標・週での都道府県の比較表、地域ページへのリンク。履歴は対象を選んだ時点で読み込む。 |
| `/municipalities/{municipality-code}/` | 公式案内や配布可能な市区町村データを確認した地域に生成する。県や保健所の情報を案内する場合は粒度と出典を表示する。市区町村の収録がないときは案内のあるページへリンクする。未生成の地域 URL は 404。 |
| `/sources/` と `/404.html` | 情報源一覧には提供元・対象・採用する資料・更新と加工の説明。404 には全国・地域一覧への復帰リンク。 |

- トップと都道府県ページでは、全国または該当する都道府県の全収録疾患の定点当たり報告数を共通の縦軸で表示する。トップではグラフの下から都道府県を検索できる。凡例には表示期間の最新週の値を示し、疾患名を選ぶと線を強調できる。月の指定はグラフと詳細表に反映し、詳細表の疾患は個別に切り替えられる。欠損週や未収録週をまたぐ線は描かない。比較用の数値は地域索引に収め、詳細履歴の取得は表示する1地域・1疾患に限る。
- 地域・疾患ページは `index.html` を生成し、直リンク・再読込・末尾スラッシュ・404・アセット・JSON の基準パスを確認する。ルート配置も試験する。
- 表・グラフ・地図では、提供元と原資料へのリンク、資料区分、対象地域・施設・期間、指標と単位、出典の更新日時と加工表示を確認できるようにする。対象週、最終取得成功、表示中の版の取得、サイト生成は別時刻。日付だけの出典に時刻を補わない。公表予定の根拠がある場合は閲覧時にも遅延を判定し、古い取得結果を現在の状態と誤認させない。
- 明示されたゼロと丸められた率のゼロ表示を残す。空欄・意味未確定のハイフン、未報告、秘匿、対象外、更新失敗、遅延を区別する。異なる週や指標を並べる画面では各値の対象を表示し、同条件の順位付けとして扱わない。公式の警報・注意報を扱う場合は公表元の判定であることを明示し、独自集計から発令を推定しない。
- 最初の閲覧経路には表とテキストを用意する。地図は境界データの再配布条件、コードと基準日、容量を確認後に追加する。色に加えてラベルやパターンと凡例を使い、欠損も表に出す。推移グラフには同じ内容の表を用意する。キーボード操作、見えるフォーカス、テキストのコントラスト、狭い画面でのリフロー、読み込み結果の通知を検証する。[WCAG 2.2](https://www.w3.org/TR/WCAG22/)

## 週次履歴の表示範囲

最新の公開対象週の終了日を基準に6暦月さかのぼり、その日以降に終了した報告週を推移と表の対象にする。6か月前に同じ日がない場合は、その月の末日を境界にする。公開対象週が更新されるたびに範囲を進める。利用できる週が6か月に満たない場合は実際の収録期間を示す。

推移の下に「6か月より前のデータは JIHS で見る」を置き、公式の年別一覧へ案内する。サイトの静的成果物には直近6か月の範囲を収める。履歴は既存の地域・月・疾患単位で分割する。[JIHS IDWR 速報の年別一覧](https://id-info.jihs.go.jp/surveillance/idwr/provisional/sokuhou.html)・[静的配信の容量検証](../findings/cloudflare-pages-history.md)

## 開発と受入

1. 開発の Go 承認後、採用技術・対象データ・承認日・フェーズを `AGENTS.md` と `docs/status.md` に記録する。架空データで正規化、公開可否、静的配信を作り、PoC からの転用部分は保守性とエラー処理を再評価する。
2. 採用候補の資料ごとに確認した範囲で原表照合を行う。条件がそろった資料だけを受入候補にし、どの表示が公式リンクに切り替わるか確認する。
3. 結合テストは正常・未許諾・欠損・訂正・旧版の再投入・容量超過を含める。ブラウザテストで直接アクセス、アセットと JSON の基準パス、狭幅、キーボード、遅延読み込み、失敗時に内容が維持されることを確認する。テスト計画と公開条件は[公開アーキテクチャ案](../architecture/mvp-publication.md)・[運用手順案](../operations/mvp-release.md)を参照。
4. 公開前に実際の成果物と運用費をレビューし、公開承認後に手動で初回を実施する。週次の運用・復旧が成立した段階で、取得頻度の許諾と承認がある提供元から定期取得を評価する。[開発 Issue 案](development-issues.md)
