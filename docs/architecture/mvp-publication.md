# 初期版の公開アーキテクチャ案

[初期版仕様](../specifications/mvp.md)と [R-17](../findings/R-17-pages-architecture.md)に基づく。Python の取得・検証・静的生成と、静的 HTML・CSS・JavaScript を第一案とする。少数ページで実測した Python PoC と共通モデルを評価の土台にする。Astro は共通 UI が増えた場合に比較し、Vite はフロントエンドのビルドが必要になった時点で再評価する。公開側は静的配信で、処理はビルド側に置く。[静的生成の比較](pages-layout.md#静的生成の比較)

取得・変換を `apps/collector/`、静的生成を `apps/web/`、共通モデルと変換規則を `packages/data-model/` と `packages/data-normalizer/` に置く候補。公開済みの小容量データを Git に置く判断をした場合だけ `data/public/` を使う。成果物 `dist/` と原本、ローカル復旧版はリポジトリの通常のコミット対象から除く。調査・運用・開発管理は同一リポジトリで継続する。

## 公開までの流れ

| 工程 | 入力・処理・結果 |
|---|---|
| 取得の許可 | データセットと対象号、公式配布先、許容する取得方式・頻度・保存期間・加工・再配布範囲、条件の根拠と日付を記録。確認できない操作は開始しない。手動起点では承認済みの入力と Git のリビジョンまたは入力ハッシュを記録する。 |
| 取得と正規化 | 公式経路を使い、サイズ・形式・期間、本文の SHA-256 と版を確認。提供元の観測値、原表の位置と記号、地域・対象範囲・単位を[共通モデル](../schemas/observations.md)へ写す。304 は使用可能な手元版を参照し、同一ハッシュの200も同じ版とする。差し替えは版付きで隔離し、根拠付きの訂正を選定する。 |
| 品質・公開判定 | スキーマ、対象週、地域・指標、キーの重複、欠損の意味、合計と原表の一致、急変の理由を確認。急変は確認対象として記録し、閾値は事前に合意した根拠がある系列に適用する。元データと表示用の許可状態を別に記録し、`allowed` の観測と許可項目から公開候補を構築する。 |
| 生成と同一版判定 | 基準パスに対応した静的 HTML、CSS、JS、比較・検索用の小さい索引、表示用 JSON を `dist/` に生成。公開内容の比較には、生成時刻など実行固有項目を除いた観測・出典・対象範囲・設定と、画面・静的アセットの内容を使う。初回公開、訂正、許可変更による削除も比較対象に含める。意味のある変更がなければ公開処理を省略する。 |
| 検証と配布 | 許可項目、ローカルパス、サイズ、ハッシュ、参照と版の一致を公開専用成果物全体で確認する。公開専用ディレクトリだけを渡す。原本・調査文書・認証情報・内部ログ・シンボリックリンク・ハードリンクは成果物の対象外。 |

## 公開ファイル

`data/manifest.json` に配布版 ID、スキーマ版、生成日時、データセット別の出典・鮮度・収録範囲、地域索引への参照を持たせる。地域索引はデータセット・粒度・地域をキーにし、対象地域の最新値と履歴ファイルへの相対パス、サイズ、SHA-256 を持つ。最新は地域・疾患別、履歴は地域・疾患・期間終了月別。データセットと粒度はパスに残し、パスは `data/` 基準とする。月をまたぐ週は終了月へ一度だけ入れ、空欄や秘匿の理由を推定で補わない。配布ファイルのパスは配布版 ID で固定する。[R-15 公開 JSON 案](../schemas/observations.md#github-pages-向け公開-json-案)・[R-17 の容量計測](../findings/R-17-pages-architecture.md#容量時間費用の試算)

ブラウザはサイトが提供するファイルだけを読み、提供元への接続は利用者が公式リンクを開いたときに限る。取得先 URL の入力は自由な URL 受付にせず、データセットごとの公式配布先から選ぶ。公開中のページが以前の配布版を参照し、履歴の読み込みに失敗したときは、既に表示した値を維持して再読み込みを案内する。

## GitHub Actions と Pages

[I-001](../findings/I-001-preview-check.md) で、架空データだけを使う読み取り専用の検証ワークフローを追加した。以下では公開を承認した後に使う構成も示す。

- 標準 Linux runner を使用する。開発時の CI は架空データのみで検証・ビルドでき、サイトを公開しない。公開を承認した後は、既定ブランチの `workflow_dispatch` を更新・復旧の入口とし、通常更新と復旧を同じ同時実行制御の対象にする。ジョブの直列化に加え、公開直前の版確認で旧候補による上書きを防ぐ。明示した復旧だけは対象版と理由を指定する。
- 公開ワークフローの取得・正規化・検証・ビルドは原則 `contents: read`。署名や書き込みが必要な別用途に権限を流用しない。同じワークフローの依存ジョブからデプロイし、`GITHUB_TOKEN` での push による別ワークフローの起動を前提にしない。
- 公開を承認したリポジトリに GitHub Actions の公開元と `github-pages` 環境を設定する。 `configure-pages` で公開先の基準パスを取得し、予算と成果物検証を通過した後に `upload-pages-artifact` を実行する。公開ジョブはビルドを `needs` で指定し、 `pages: write`・`id-token: write` をここだけに与え、`deploy-pages` で配布する。対象ブランチを環境の保護条件に設定し、使用する Action はフルコミット SHA に固定する。[Actions 公開元](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)・[Pages のカスタムワークフロー](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)
- 公開先の manifest、代表地域ページ、最新 JSON の版・ハッシュを照合して公開成功を記録する。実行結果が不明な間は後続の公開を保留する。[予算・更新・復旧手順案](../operations/mvp-release.md)
