# データ取得・公開と障害復旧の運用案

[R-16 の資料別の条件と観測結果](../findings/R-16-collection-operations.md)に基づく。期間・鮮度・公開可否の項目は [R-15 の共通モデル案](../schemas/observations.md)に対応する。ここで示す時間と保持期間は初期設定の候補。

## 取得の開始条件と実行範囲

1. データセットごとに、提供元、公式の掲載ページ・配布リンク、対象ファイル、許容された取得頻度と用途、保存・加工・再公開の判断、確認日を登録する。前提が不明な資料は、手動の公式リンク確認を続ける。定期実行と公開は該当する条件の確認後に承認を得る。
2. 公表予定は JIHS 速報の更新欄と厚労省の直近号の次回予告に従う。初期案は提供元ごとに予定日の夕方に1回だけ確認する。休日・曜日変更は日付を調整する。予定日の翌営業日まで更新を確認できないときは通知し、手動で掲載先と次回予告を確認する。事前に許容回数を決め、予定時刻の経過だけで監視頻度を増やさない。
3. 提供元ごとに同時実行は1。リクエストは接続5秒、全体20秒を初期候補とし、ファイルサイズ・リダイレクトの上限と許可する配布先を事前設定する。リダイレクト先は許可した公式の配布元に限る。タイムアウト・一時的な 5xx は許容回数に余裕がある場合にだけ、60〜90秒空けて1回まで再試行する。提供元の条件がより厳しい場合はそちらを採用する。
4. 401・403・429・CAPTCHA では対象資料の取得と再試行を停止し、発生時刻、URL、応答状態、`Retry-After` があればその値を記録する。原因と許容条件を確認してから手動で再開を判断する。404 は掲載一覧から移転・未掲載を確認する。出力の HTML への切替、形式違い、規約変更が見つかったときも検証へ進めず保留する。
5. GitHub Actions を採用する場合は毎時00分を外す。予定時刻は JST として管理し、設定・ログで UTC と照合する。定期実行が遅延・未実行となる可能性があるため、予定からの経過と最終成功の双方で監視する。公開リポジトリの無活動による自動無効化と、有効化・手動実行の方法を運用手順に含める。公開処理は一つずつ実行し、手動実行との競合も同じ制御の対象にする。[GitHub の schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)・[同時実行制御](https://docs.github.com/en/actions/concepts/workflows-and-actions/concurrency)

## 再取得と訂正

1. 公式の掲載一覧・週別ページから実ファイルを選ぶ。取得の日時、資料種別、報告年・週または号、URL、HTTP 状態、ヘッダー、SHA-256、抽出手順の版を記録する。`ETag` または `Last-Modified` は同じ URL・同じ表現に対してだけ再利用する。
2. `304` では利用できる手元版があることを確認し、再確認時刻を更新する。本文取得時刻や公表日を変更しない。再確認時刻は `last_source_checked_at` の候補とし、R-15 の取得成功時刻とは区別する。手元版が使えない場合は運用上の取得失敗として扱い、許可された取得枠で改めて本文を取得する。`200` は形式、サイズ、対象表・対象週を確認し、SHA-256 が同じ場合は同じ原本版を参照する。形式を確認できる本文の取得時刻と、実際の公開版に対応する取得時刻は分ける。
3. ハッシュ差分があれば、同一データセット・同じ号・資料種別の候補版を隔離し、対象期間、表の構造、原表値と正規化後の差分を確認する。掲載先 URL が変わっても同じ号であれば照合する。公式の訂正理由が不明なら差し替えの観測と明示し、理由を推定しない。値が異なる速報・週報・年報を同じ軸で比較するには、定義と期間が一致することを先に確認する。
4. 厚労省の前報と当報は別の号として保持する。報告された累計の変動はその版の値で記録し、前週に配分しない。訂正済みの過去週を採用した場合は、旧版・新版の関係、差分、出典と採用日時を記録する。

## 公開判定と障害の切り分け

1. **候補を作成する。** 取得・正規化・品質検査・公開可否判定を通過したデータセットの版だけを候補に含める。公開対象、元資料、承認の根拠、適用した加工条件を検証する。原本・内部ログ・未許諾の値は公開バンドルに含めない。
2. **公開候補一式を検査する。** 版 ID ごとに HTML・JSON・manifest を生成し、全参照ファイル、SHA-256、出典、地域・期間、直リンクを検査する。バンドル作成と本番切り替えを分け、公開前に全体を揃える。実行を再開する場合は、版 ID とハッシュが同じ処理の二重登録を防ぐ。
3. **失敗時の公開中データを確認する。** 取得・検証・生成の失敗では候補を採用せず、最後に検証と公開に成功した完全な版を維持する。規約・権利変更で以前の版も許可条件を満たさない場合は、そのデータを公開から外す対応を承認者へ引き継ぐ。最初から公開可能な版がない場合は値を表示しない。
4. **失敗範囲と対象期間を案内する。** 公開 JSON・表示では、対象期間、提供元の更新日、最終確認・取得成功、公開中の版の取得時刻、サイト生成を別々に示す。失敗の直後に再公開できない場合は、既存版が最後に記録した時点を表示し、管理者向けに別経路で通知する。古い manifest の運用状態を現在の状態として表示しない。
5. **部分更新の条件を確認する。** 提供元を跨いだ結合を必要としないデータセットのみを候補とする。影響を受けたデータセットは公開可能な旧版から引き継ぎ、データセット別の対象期間・版・状態を明示する。全ファイルを新しい配布版の一式に揃え、manifest の参照切れを検査する。片方の古い値を新しい対象日や0として埋めない。依存する系列の揃いが必要な場合は一式を据え置く。

| 起点 | 初動 | 復旧の確認 |
|---|---|---|
| 公表予定を過ぎても掲載されない | 最終成功時刻と公式の次回予告を確認。既存の集計を維持し、予定と実績を記録 | 正式リンクが出た時点で対象期間を再確認し、許容枠内で手動取得 |
| 取得失敗・アクセス拒否 | 対象の提供元を停止または保留し、HTTP 状態と許容条件を確認 | 原因が解消したことを確認し、承認済みの操作と回数内で手動実行 |
| 列変更・集計不一致・訂正 | 候補版を隔離し、対象週、脚注、訂正案内、差分を照合。公開中の版を維持 | 確認済み変換手順で再実行し、原表照合と公開条件の検証を通す |
| デプロイ失敗・結果不明 | 新しい公開処理をいったん止め、実行結果と公開 URL の manifest の配布版 ID を確認 | 参照先まで照合し、不整合なら保存済みの検証・公開成功版一式を再投入。公開 URL で版 ID・主要 JSON・地域ページを確認 |
| 公開条件の変更・取り下げ | 影響版と配布経路を確認し、公開停止・削除を承認者へ引き継ぐ | 対象を外した版の公開を確認し、旧版・保管・ログ・外部キャッシュへの影響を確認する |

通知には提供元、対象周期、工程、理由と現在の公開版、次の判断を記載する。復旧では新しい取得を行う前に、過去の成功版が再利用可能か確認する。ロールバックは成功版の一式を再投入し、公開 URL の確認後に成功として記録する。承認が必要な利用・権利の判断は自動的に復旧しない。

## 保存先と保持期間の候補

| 種別 | 試験段階の候補 | 削除と例外 |
|---|---|---|
| 原本・未採用候補 | 許可されたものだけ一時領域で検証。継続運用ではアクセス制限のある、削除期限を設定できる外部保管を候補とし、直近90日を比較の起点とする | 個別条件・撤回が優先。許可のない原本と候補版を公開 Git・Actions ログへ入れない |
| 公開成功版 | 現行と直前2つ以上の完全な配布版を、運用担当が明示的に管理・取得できる保存先に保管する案。保持は件数と復旧に必要な実日数を確認して決める | 撤回された版を復旧候補から除く。サイトの表示用履歴、復旧用の配布版、原本はそれぞれ保持条件を決める |
| Actions のキャッシュ・artifact | ビルド再利用や一時的な引き渡し用。保存期限のあるログと artifact だけに復旧を依存させない | artifact の削除・期限と、復旧候補を別に管理する。[GitHub の artifact 保持](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts) |
| Git | スキーマ、手順、架空データ、公開を承認した必要最小限の生成物を候補とする。原本・履歴の既定の保管先は削除可能なストレージを優先 | 削除コミット後も過去のコミットやクローンに残り得る。公開前に履歴、Issue、ログ、成果物を点検する。[GitHub の Git 履歴からの削除](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository) |

保存先・件数・期限・費用と、実際の Pages 上での公開・復旧は R-17 で架空データを使って検証する。
